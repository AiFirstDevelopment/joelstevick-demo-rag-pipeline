**book-02** If an LLM keeps nothing between requests, how does a chat app seem to remember what I said earlier?

> The model itself keeps nothing between requests, and every request is answered from scratch using only what that request contains. The apparent memory comes from a program on the other side that keeps an array of the messages and resends it each time. The array holds your messages and the model's own replies, so each new request carries the whole conversation so far, sent in full. If the model's reply is left out of the array, the next request reads as two user statements with no answer between them.

**book-11** What's the catch with copying a shared checker script into every repo so CI can run it?

> The catch is that a vendored copy is frozen on the day it was made. **book-15** At what levels can a rule be enforced, from weakest to strongest?

> A rule can be enforced at three levels, from weakest to strongest: the prompt, the hook, and continuous integration (CI). Even CI only becomes a gate once a required status check and branch protection are set in the repository host, and those settings cannot be committed in the repository. Layer one is the prompt, a numbered prohibition in a system prompt. It shapes behaviour most of the time but fails unattended, under pressure, with an articulate justification available. Layer two is the hook, a program a tool calls at a defined point whether or not anybody remembered it. Its weakness is that it runs on somebody's machine, and `git commit --no-verify` skips every one. Layer three is CI, which runs your checks on its own machines using the repository's committed configuration, so nothing on a developer's laptop can switch it off.

**book-19** Why does the book recommend having the model grade its own work as the main quality check?

> The book does not recommend this; it says the opposite, that nothing grades its own work. **book-21** Why does the book say a twenty-round agent loop costs about twenty times a single request?

> The book does not say that; it says a twenty-round loop does not cost twenty times one request, but closer to two hundred. The reason is that you send the entire conversation on every turn, and the transcript keeps growing. In its example, a twenty-turn run over a transcript that ends at 40,000 tokens sends roughly 400,000 input tokens, because the average turn carried half the final transcript. So cost grows roughly with the square of the number of turns rather than in a straight line.


**boundary-01** What does max_tokens do, and what happens to the response if the ceiling is hit?

> `max_tokens` is a required, hard ceiling on how much the model may produce in one response, and it is measured in output tokens. If the model reaches it, the response simply stops, mid-sentence if necessary. The API reports `max_tokens` as the stop reason, meaning the response was cut off mid-thought. A cut-off response is a truncated answer that looks like an answer, because its text is populated and then stops.


**boundary-02** The weights were fitted on text gathered up to some point in time: what is that point called, and what does the model know after it?

> The point is called the training cutoff. After it the model knows nothing, and it cannot tell "after my cutoff" apart from "does not exist". So if you ask about something newer, it won't say "I don't know" but will give a fluent, plausible answer.


**boundary-03** The book says sycophancy is not politeness and not indecision. What is it then, and where does the tendency come from?

> Sycophancy is a model's tendency to move towards the position it believes its interlocutor holds, rather than towards the position the evidence supports. It is a learned pattern. Text in which a speaker accommodates a disagreeing counterpart is very common, and agreeable continuations were reinforced during training because human raters preferred them.


**boundary-04** What is fail-first verification, and why does it matter more when a model writes the code or the tests?

> Fail-first verification is proving that a test fails when the behaviour it guards is broken, before trusting it to guard anything: you break the code, run the test, see red, restore, and see green. It matters more when a model is involved because a test that cannot fail is exactly what an optimiser under pressure produces when asked to make a suite pass. A model asked to "add tests for this change" produces tests that check nothing at a noticeable rate, and they look just like real ones, so the only way to tell is to break the code and see whether they notice. In this pipeline a test is finished only when it has been observed to fail for the right reason.
