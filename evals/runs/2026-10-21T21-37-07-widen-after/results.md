**book-19** Why does the book recommend having the model grade its own work as the main quality check?

> The book does not recommend this; it says the opposite: "Nothing grades its own work." A grader whose only input is the thing being graded is a text generator with a strong prior towards approval, so it will very often print PASS even when a case is unhandled. Instead it recommends checks that do not depend on the model's opinion of its own output: write down what "done" means first, have a separate reader examine the work, make someone decide, and let machines check what they can.

**boundary-01** What does max_tokens do, and what happens to the response if the ceiling is hit?

> max_tokens is a required, hard ceiling on how much the model may produce in one response, measured in output tokens. If the model reaches it, the response simply stops, even mid-sentence, and the stop reason is reported as max_tokens. The text looks like a real answer but is truncated, so the loop in the book treats it as an error rather than a completion.


**boundary-02** The weights were fitted on text gathered up to some point in time: what is that point called, and what does the model know after it?

> That point is called the training cutoff. After it the model knows nothing, and it cannot tell "after my cutoff" from "does not exist," so it gives a fluent, plausible-sounding answer instead of saying "I don't know."


**boundary-03** The book says sycophancy is not politeness and not indecision. What is it then, and where does the tendency come from?

> Sycophancy is a model's tendency to move towards the position it believes its interlocutor holds, rather than towards the position the evidence supports. It is a learned pattern: text in which a speaker accommodates a disagreeing counterpart is very common, and agreeable continuations were reinforced during training because human raters preferred them.


**boundary-04** What is fail-first verification, and why does it matter more when a model writes the code or the tests?

> Fail-first verification is proving that a test fails when the behaviour it guards is broken, before trusting it to guard anything: break the code, run the test, see red, restore, see green. It becomes non-negotiable when a model writes the code or the tests, because a test that cannot fail is exactly what an optimiser under pressure produces when asked to make a suite pass. Such tests are hard to spot by reading, since they look identical to real ones, so the only way to tell is to break the code and see whether they notice.
